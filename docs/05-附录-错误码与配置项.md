### 1.6 错误码问题汇总

1. **同码不同义**：`9999` 同时表示“非允许渠道”和“兜底异常”；`9991` 同时表示“PROCESS 未启动”和“交易码为空”；`999` 多处复用。
2. **非数字码**：`6s532` 不符合“错误码为数字字符串”的常规约定。
3. **消息不统一**：同类错误有“报文转化错误”“转换失败”“解析有误”多种描述。
4. **缺少分段规范**：建议按模块分段，例如：
   - `1xxx` 接入与治理；
   - `2xxx` 路由与配置；
   - `3xxx` 报文转换；
   - `4xxx` 出站与通信；
   - `5xxx` 安全与密钥；
   - `9xxx` 系统级异常。
5. **缺少响应结构规范**：HTTP 入口既有 JSON 对象、又有 XML、又有定长串，错误响应结构不统一。

## 3. 报文样例

### 3.1 JSON 渠道请求 → 第三方请求（示意）

渠道请求（外层 `data` 为业务报文字符串）：

```json
{
  "tranNo": "TRANNO001",
  "channel": "CH01",
  "nonce": "20220113111106500001",
  "timestamp": "202201131111060000",
  "digestAlgorithm": "SM3",
  "data": "{\"transaction\":{\"header\":{\"msg\":{\"sndDt\":\"20220113\",\"seqNb\":\"111106500000497\"}},\"body\":{\"request\":{\"orderId\":\"O123\"}}}}"
}
```

第三方请求（由 Tag 映射生成，示意）：

```json
{
  "transaction": {
    "header": { "msg": { "sndDt": "20220113", "seqNb": "111106500000497" } },
    "body": { "request": { "orderId": "O123" } }
  },
  "tranNo": "P001"
}
```

### 3.2 XML 渠道请求

```xml
<?xml version="1.0" encoding="UTF-8"?>
<transaction>
  <header>
    <msg><seqNb>111106500000497</seqNb></msg>
  </header>
  <body>
    <request><orderId>O123</orderId></request>
  </body>
</transaction>
```

响应封装格式：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<transaction><code>0000</code><message>成功</message><data>...</data></transaction>
```

### 3.3 定长报文示意

请求：`[10位交易码][业务数据]`

```text
TRANNO001                      O123...
```

响应：`[6位长度][业务数据]`

```text
000012000000 success
```

> 定长字段长度与顺序完全由 Tag 表的 `sort`、`taglength` 决定。

### 3.4 TCP 帧

```text
请求： 000123{"tranNo":"TRANNO001","channel":"CH01",...}
响应： <现状> 不带长度头；<目标建议> 000045{...}
```

## 5. 文档维护建议

1. 错误码字典应随代码变更同步更新，建议由统一枚举类生成。
2. 配置项清单要与 `application-*.yml` 模板一起维护。
3. 报文样例应作为契约测试的输入/期望输出，避免文档与实现漂移。
