## 3. P0：阻断构建或导致数据错误

### P0-01 Maven 子模块路径错误（已修复）

- **原证据**：`xrpc-common/pom.xml` 曾声明 `<module>xrpc-module-esb-service</module>`，但该目录实际位于 `xrpc-module/xrpc-module-esb-service`。
- **影响**：根目录执行 `mvn clean package` 时 reactor 报“Child module ... does not exist”，无法构建。
- **当前状态**：该 module 声明已从 `xrpc-common/pom.xml` 移除；`esb-service` 不再被任何 reactor 引用。其 pom 的 parent 已补充 `<relativePath>../xrpc-common/pom.xml</relativePath>`，避免单独构建时父 POM 解析错误。
- **建议**：若确认 `esb-service` 已废弃，可直接归档整个目录。

### P0-02 process 与 esb-service 重复实现

- **证据**：改造前两个模块均有 `DefaultAbstractServiceRedis`、`DefaultService`、`MapConvert`、`StringMapServe`、`DC*Util`；`esb-service` 版的 `filter()` 已迁入 process 并统一改名为 `DefaultAbstractService`，`esb-service` 已归档。
- **影响**：修复只落一处会导致行为分叉；启动类日志都打印 "xrpc-module-process"，难以辨识。
- **建议**：确认唯一有效版本（当前 process 被 accept-http 通过 URL 调用，实际生效），将另一份标记为 deprecated 或从构建中移除；保留差异点（如 `filter()`）的迁移清单。

### P0-03 TCP 接入响应缺少长度头

- **证据**：
  - 接入：`accept-tcp-*/NioServer.handleRead` 请求按“6 位长度 + 报文”解析，但写回时仅 `buffer.put(response.getBytes())`；
  - 出站：`send-tcp/DefaultSocketClient.forwordMess` 读取响应时先读 `fixedlength` 位长度。
- **影响**：两端帧协议不对称，按统一客户端解析时会错位或超时。
- **建议**：统一帧协议；目标格式统一为 `[N位十进制长度][报文体]`，长度按字节计算；增加最大报文限制与半包处理。

### P0-04 HTTP 端口冲突

- **证据**：`accept-tcp-json/application.yml` 与 `send-tcp/application.yml` 都配置 `server.port: 9305`。
- **影响**：两个进程不能同时启动。
- **建议**：重新规划端口，例如 JSON 接入 HTTP 改为 9307，TCP 监听保持 9999。

### P0-05 TCP 接入静态配置键缺失

- **证据**：
  - `accept-tcp-json/Static.java` 读取 `${url.xrpc-module-accept-http-json}`，但其 `application-static.yml` 只有 `url.xrpc-module-accept-http`；
  - `accept-tcp-xml/Static.java` 读取 `${url.xrpc-module-accept-http-xml}`，同样缺失；
  - `accept-tcp-dc` 配置键完整。
- **影响**：Spring 启动占位符无法解析，json/xml 接入服务启动失败。
- **建议**：按 dc 模块的键格式补齐三个 URL，并把监听端口键与实际模块对齐（当前 json 模块的 `initNameDk` 读取的是 `${url.xrpc-module-accept-tcp-xml}`，存在复制粘贴错误）。

### P0-06 加解密 Key Hash 名不一致

- **证据**：`InitController.getcey` 写 `RedisUtils.setHashKV("SMKEY", channel, decStr)`；`Decryption.check` 读 `RedisUtils.getHashKV("SIMKEY", channel)`。
- **影响**：任何开启 `isCryption` 的交易都无法取得密钥，解密失败。
- **建议**：统一为 `SMKEY`（或 `SIMKEY`），并抽取常量；补充端到端加解密测试。

### P0-07 SM2 私钥路径硬编码

- **证据**：`InitController.getcey` 中 `SM2Utils.importPrivateKey("F:/sm2/private_key.pem")`。
- **影响**：换环境即失败；私钥落在开发机路径，不合规。
- **建议**：改为配置项或密钥管理服务；禁止私钥进入代码库；支持多环境密钥与轮换。

### P0-08 并发计数只增不减

- **证据**：`channel.check` 把 `new BinFaBean(...)` 加入 `Static.nonce`，但所有 controller 的成功/异常分支都没有对应移除逻辑。类注释也写明“需要在返回时清除”。
- **影响**：运行一段时间后渠道/接口并发数只增不减，所有请求被判超限。
- **建议**：用 `try/finally` 在请求结束释放；计数改为 `AtomicInteger` 或 Redis `INCR/DECR` + 过期时间；异常路径也必须释放。

### P0-09 定时清理任务并发异常与计算错误

- **证据**：`Static.deleteGq` 在增强 for 循环中 `nonce.remove(nonce_)`；分钟差用 `(hour2-hour1)*60 + (minute2-minute1)`，跨小时会得到负值；日志写“5分钟”，cron 与判断写“3分钟”。
- **影响**：`ConcurrentModificationException`；跨时段清理失效或误清理；运维口径不一致。
- **建议**：使用 `Iterator.remove()` 或线程安全集合；用 `System.currentTimeMillis()` 计算时间差；统一阈值并写进配置。

### P0-10 流水号防重两套存储且生命周期不一致

- **证据**：`UniqueSerialNumber` 使用 `StructureUtil.getNonce/setNonce`（Redis 普通 KV TTL 5 秒，map 模式内存 Map）；`channel` 使用 `Static.nonce`（3 分钟定时清理）。
- **影响**：防重窗口与并发窗口不一致；map 模式流水号永不清理导致内存泄漏；Redis 5 秒窗口远短于注释中的“5 分钟”。
- **建议**：统一防重存储，设置与业务约定的 TTL（例如 5 分钟）并使用原子 `SETNX`；并发计数与防重解耦为两个独立数据结构。

## 4. P1：可靠性、安全与性能

### P1-01 内部接口无认证

- **证据**：所有 Controller 无 Spring Security 依赖；`process/defaultController` 与 `CrudBaseController` 一旦挂载即可被直接调用。
- **建议**：最小改动可加网关层 mTLS + 接口签名；中期引入认证中心；管理接口必须鉴权与审计。

### P1-02 签名字段未使用

- **证据**：`Dto`、`CustomerReq`、`CustomerRes` 定义 `sign`、`smSign`、`digestAlgorithm`、`key`，代码中无验签实现。
- **建议**：明确验签算法与覆盖字段范围，接入前校验；失败返回统一错误码。

### P1-03 时间戳校验可绕过

- **证据**：`Timestamp.check` 中 `timestamp` 为空/长度不为 18 时抛出异常的代码被注释，直接放行。
- **建议**：强制校验；与 nonce 绑定，防止重放。

### P1-04 缺少超时、重试、熔断

- **证据**：`ConfigBean.restTemplate()` 直接 `new RestTemplate()`，未设置连接/读取超时；无 Resilience4j/Sentinel 实际接入。
- **建议**：统一客户端配置；按交易码配置重试次数、熔断阈值与降级响应。

### P1-05 OkHttp 客户端不复用

- **证据**：`OKHTTPUtil` 每个方法内 `new OkHttpClient()`。
- **影响**：连接池无法复用，频繁建连，TIME_WAIT 增多。
- **建议**：使用静态单例 Client；超时参数化；关闭响应体。

### P1-06 NIO 单线程阻塞

- **证据**：`NioServer` 单 Selector 线程中直接调用同步 `OKHTTPUtil`；缓冲区固定 10KB；一次 read 即按 6 字节长度解析。
- **影响**：慢请求阻塞所有连接；大报文失败；半包/粘包无法处理。
- **建议**：NIO 只做帧收发，业务处理交线程池；使用长度字段累计读取；最大报文限制；考虑 Netty。

### P1-07 无幂等与补偿

- **证据**：nonce 仅存 Redis 5 秒或内存；第三方调用成功后若响应映射失败，`06987` 直接抛出，无补偿记录。
- **建议**：幂等键持久化；本地消息表或事务消息；失败进入死信队列可重放。

### P1-08 日志同步写库且流水不完整

- **证据**：`LogServe.log` 直接 `baseService.save`；`JsonController` 先写请求日志，再执行过滤器；同一 `EsbTranLog` 实例在请求/响应两次 save。
- **建议**：一次请求一条流水，先生成记录，结束/异常时更新；异步写库；记录耗时与响应码。

### P1-09 敏感信息与配置明文

- **证据**：`application-datasource.yml` 数据库密码明文；`redis.properties` 地址明文；请求/响应报文写入日志；Hibernate SQL 绑定参数开启 TRACE/DEBUG。
- **建议**：敏感配置加密或环境变量注入；生产环境关闭 SQL 参数日志；日志脱敏规则配置化并审计。

### P1-10 XML/JSON 解析安全

- **证据**：`XML.toJSONObject`、`new JSONObject(data)` 无报文大小/深度/外部实体限制；`MapConvert` 递归无环检测。
- **建议**：禁用 XML 外部实体；限制报文长度与嵌套深度；JSON 解析使用安全配置；对 Tag 配置做环检测。

### P1-11 元数据缓存无刷新且双实现同时加载

- **证据**：`DataStructureCache` 与 `DataStructureRedis` 均为 `@Component` 且 `@PostConstruct init()`；无论 `cacheName` 取值都会执行；静态 Map 无更新入口。
- **建议**：按 `cacheName` 条件加载（`@ConditionalOnProperty`）；抽象统一接口；支持版本号与热刷新；增加缓存未命中告警。

### P1-12 Redis 使用问题

- **证据**：`RedisUtils.getHashKVForByte` 使用 `getWriteJedisObject()`；`SerializeUtil` 使用 Java 原生序列化；`redis.properties` 中 `testOnBorrow=2`、`testOnReturn=2`。
- **影响**：读写池语义混乱；序列化跨版本脆弱；布尔配置实际解析为 false。
- **建议**：读走读池；改用 JSON/Protobuf 序列化；修正布尔配置；增加连接池监控。

### P1-13 文件监听路径错误

- **证据**：`PortMap.init()` 调用 `watchFile(cportfilepath)`，传入的是文件路径；`BizFlagCache.init()` 传的是父目录，用法正确。
- **建议**：`PortMap` 传父目录，并在回调中判断变更文件是否为目标文件。

### P1-14 日志配置问题

- **证据**：`logback.xml` 中存在两个 `<root>` 节点；日志路径硬编码 `d:/logs`；`LogIntercept` 结束日志打印 `startTime`；多处 `System.out.println` 与 `e.printStackTrace()`。
- **建议**：合并 root；日志路径参数化；修正耗时计算；统一使用 Logger。

## 6. 建议改造顺序

```mermaid
flowchart LR
    A[阶段一：修复 P0<br/>构建/协议/配置/密钥/计数] --> B[阶段二：稳定性<br/>超时/连接池/幂等/缓存刷新/错误码]
    B --> C[阶段三：安全合规<br/>认证/验签/密钥管理/脱敏/审计]
    C --> D[阶段四：平台化<br/>管理后台/监控/灰度/测试体系]
```

### 阶段一最小可交付清单

1. 修正 `xrpc-common/pom.xml` 模块声明；
2. 删除或归档 `esb-service`，保留差异点迁移说明；
3. 统一 TCP 帧格式并补齐 json/xml 配置键；
4. 调整 9305 端口冲突；
5. 统一 `SMKEY`，私钥路径配置化；
6. 并发计数 finally 释放 + 线程安全集合；
7. 流水号统一 Redis SETNX + 合理 TTL。

### 阶段二验收标准

- 全链路错误码唯一且可查；
- 第三方调用有超时与降级；
- 元数据变更可在约定时间内生效；
- 一笔交易一条完整日志；
- 黄金报文回归测试通过。

## 7. 风险提示

1. 修复 P0-08/P0-10 会改变限流与防重行为，需与业务确认窗口时间。
2. 统一 TCP 帧格式需要同步改造所有对端系统，必须灰度发布。
3. 移除 `esb-service` 前需确认没有外部进程直接调用它的 9301 端口或特定 Bean。
4. 启用认证与验签属于契约变更，需提前通知渠道方。
