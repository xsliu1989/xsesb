## 排查 TRANNO001 联调报文报错（POST 9300/controller/jsonHandler）
- 用户报文：tranNo=TRANNO001, channel=CH01, 固定 nonce=2026112511505356099396, timestamp=202611251150532810, data=JSON。
- 实测返回与根因（对照实验坐实）：
  - 原 nonce 首次 → `863 唯一流水号重复`：`StructureUtil.getNonce` 用内存 Map 判重、无过期（cache.cacheName=map），该 nonce 已被之前请求写入。换全新 nonce 即可过。
  - 新 nonce + channel=CH01 → `9999`（message 空）：`channel` 过滤器调 `getConnectCountByChannel(dto.getChannel())` 传 "CH01"，但 `DataStructureCache.initCustomerChannel()` 按 `cs.getSystype()` 建索引，样例数据 systype 全是 "CHANNEL"，取到 null → NPE → JsonController 兜底 9999。
  - 新 nonce + channel=CHANNEL → `999`：过了 channel 过滤器，但 `isChannel` 里 `sysName.indexOf(dto.getChannel())`（交易 sysName="CH01,CH02"）匹配不到 → DefineException 999。
- 数据源关键：ESB 元数据只在 accept-http / process 启动时从 DB 加载到内存 Map；`sql/06-挡板联调-TRANNO001.sql` 是专门为本交易准备的联调脚本（改 sysname=CH01、iscryption=false、isOpen=true、datatype=xml、sendurl=挡板地址，并重建四段 Tag）。执行后必须重启 accept-http 和 process 才生效。
- 注意 `04-demo-data.sql` 中 TRANNO001 的 sysname="CH01,CH02"、iscryption="true"，会让 isChannel/Decryption 失败；06 脚本正是修正这些。
- 结论：这是配置/数据问题 + 缓存 key 设计缺陷（systype vs sysname 混用），非代码功能 bug。完整联调需先跑 06 脚本再重启两个服务；日志输出到启动控制台，logs/xrpc-module-accept-http/error.log 是空的。

## 修复 Redis 未启用时 process 启动失败（20:10）
